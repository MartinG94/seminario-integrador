# Constitución — SGD-AVEIT

Principios innegociables del proyecto. Toda especificación (`spec.md`), plan técnico (`plan.md`) y tarea (`tasks.md`) debe cumplirlos estrictamente.

1. **La spec manda:** Ningún comportamiento, endpoint, modelo o componente se implementa si no está especificado en la spec activa dentro de `specs/`. Si falta una definición reglamentaria o técnica, se detiene el trabajo y se consulta al Product Owner.
2. **Integridad transaccional y cero UPDATE manual:** Queda terminantemente prohibida la modificación manual o directa de saldos de puntos y expedientes mediante sentencias SQL (`UPDATE`/`DELETE`) sobre la base de datos MySQL. Toda mutación de saldo debe ejecutarse como un asiento transaccional inmutable en el libro mayor de auditoría, respaldado por un acto resolutivo o rectificatorio formal.
3. **Tests como puerta de calidad:** Cada tarea termina indefectiblemente con sus tests automatizados en verde (`pytest` para backend con cobertura mínima del 80% sobre la lógica de negocio; `Karma`/`Jasmine` para frontend). Prohibido abrir Pull Requests o avanzar a la siguiente tarea con tests fallando o ausentes.
4. **Arquitectura desacoplada y dominio puro:** La lógica jurídica y procesal (cómputo de plazos preclusivos de 5 días hábiles, control de mayorías, baremos y alertas escalonadas) reside en servicios de dominio desacoplados, independientes del framework web y testeables de forma aislada. La SPA Angular solo consume contratos REST tipados.
5. **Alineación con el Sistema de Diseño AVEIT 2026:** Toda interfaz web debe adherir rigurosamente a los tokens de color, gradientes, tipografías y elevaciones especificados en `DESIGN.md` (Material Dashboard PRO), garantizando diseño Mobile-First y cumplimiento de contrastes bajo norma WCAG 2.2 AA.
6. **Conformidad estatutaria ineludible:** El sistema debe reflejar sin desvíos los 6 estados oficiales del expediente (Reglamento Procesal 2026), los formularios oficiales (T01, T02, T03), el requisito de firma colegiada de Socios Activos y los umbrales de alarma (7 puntos preventiva, 10 puntos crítica de pérdida automática de condición de socio según el Art. 93 del Reglamento Interno).
7. **Idioma y convenciones:** Código fuente, nombres de variables, funciones, clases, tablas, migraciones y commits en inglés. Mensajes dirigidos al usuario, etiquetas de interfaz, documentación formal y textos reglamentarios en español institucional.
8. **Terminología societaria canónica:** La categoría **Pasivo** equivale a la denominación anterior **Junior** y comprende los años sociales 1.º a 3.º; la categoría **Activo** equivale a **Senior** y comprende los años sociales 4.º a 6.º. La interfaz y la documentación nueva deben usar `Pasivo`/`Activo`. Esta categoría no debe confundirse con la vigencia de una cuenta o membresía, que se modelará por separado como habilitada/vigente o inactiva/no vigente.
